# زعيم الملاعب — مشروع أندرويد مولّد من APK Studio

هذا مشروع أندرويد أصلي (Java + Gradle) وليس غلافاً بسيطاً: شاشة بداية مرسومة بعناصر أصلية،
تكامل AdMob الرسمي، ملء شاشة غامر، سحب للتحديث، حقن JavaScript، وعمل بدون إنترنت.

- **معرّف الحزمة:** `com.mystudio.app`
- **رابط التشغيل:** https://mo-fashwan.base44.app
- **الوضع:** معرّفات AdMob تجريبية (استبدلها قبل النشر)

## أسرع طريقة للحصول على APK (بدون تثبيت أي برنامج)
1. أنشئ مستودعاً جديداً على GitHub وارفع كل ملفات هذا المجلد إليه.
2. سيعمل الإجراء الجاهز `.github/workflows/build-apk.yml` تلقائياً عند أول رفع.
3. من تبويب **Actions** افتح آخر تشغيل ثم حمّل الملف **apk** — ستجد نسخة debug ونسخة release.

## البناء على جهازك (Android Studio)
1. افتح Android Studio ثم **Open** واختر مجلد المشروع.
2. للنسخة الكبيرة الأوفلاين، شغّل من مجلد المشروع: `python3 tools/snapshot_site.py` (Python 3 مطلوب). في GitHub تُنفّذ هذه الخطوة تلقائياً.
3. انتظر مزامنة Gradle (قد يطلب توليد Gradle Wrapper — اضغط Fix/OK).
4. من القائمة: **Build → Build Bundle(s) / APK(s) → Build APK(s)**.

## قبل النشر على Google Play
- غيّر معرّفات AdMob من لوحة AdMob إلى معرّفات حقيقية (ملف `AppConfig.java`).
- أنشئ مفتاح توقيع خاص بك واستبدل `signingConfig signingConfigs.debug` في `app/build.gradle`.
- حدّث رقم الإصدار عند كل نشر.

## الإعلانات يطلبها الموقع (JS Bridge)
الموقع هو من يطلب الإعلان، ولا يُعرض أي إعلان بيني تلقائياً:
- `AndroidApp.isInterstitialReady()` — هل الإعلان البيني جاهز؟
- `AndroidApp.showInterstitial()` — يطلب عرضه فقط إذا كان جاهزاً؛ true تعني قبول الطلب وإرساله إلى Main Thread، لا ضمان نجاح عرض الإعلان من جوجل. لا ينتظر الجسر نتيجة العرض ولا يحجب JavaScript.
- `AndroidApp.showInterstitialOnNextPageLoadIfReady()` — الخيار الحالي لطلب العرض عند التحميل التالي، ولا يُفعّل إلا بطلب الموقع.
- `AndroidApp.isRewardedReady()` / `AndroidApp.showRewarded()` — الإعلان المكافِئ.
- `AndroidApp.showBanner()` / `AndroidApp.showBannerAt("top"|"bottom")` / `AndroidApp.hideBanner()` — البانر طبقة عائمة فوق المحتوى.
- `AndroidApp.reload()` / `AndroidApp.toast("...") ` / `AndroidApp.isOnlineNow()`.

## تشخيص دورة AdMob الأصلية على Android
- يجب توليد المشروع وبناء APK جديد وتثبيته؛ تحديث الاستوديو وحده لا يحدّث APK مثبتاً سابقاً.
- السجل NativeBuilderAds يفصل consent_begin / consent_complete عن sdk_initialize_begin / sdk_initialize_complete ثم interstitial_load_requested / interstitial_loaded / interstitial_show_requested / interstitial_shown / interstitial_dismissed؛ وبالمثل للإعلان المكافئ.
- لعزل التهيئة دون تحميل إعلانات: في نسخة تشخيصية أبقِ ads.enabled مفعّلاً وعطّل banner/interstitial/rewarded جميعاً من إعدادات المشروع الحالية، ثم أعد البناء. بعد ذلك فعّل كل نوع منفرداً للمقارنة؛ لا تغيّر منطق الموقع أو استدعاءاته. عدم عرض إعلان لا يعني عدم تحميله مسبقاً.
- على جهاز Android، استخدم معرّفات Google التجريبية، وانتظر جاهزية الإعلان، ثم اجعل الموقع يطلبه كالمعتاد، وأغلقه وواصل اللعب والتنقل؛ كرر 3 مرات على الأقل. هذه خطوات اختبار مطلوب تنفيذها وليست نتيجة اختبار أجري داخل الاستوديو.
- يجب أن يظل رقم webView في NativeBuilderWebView ثابتاً خلال activity_pause / activity_resume، وألا يحدث activity_create أو activity_destroy أو page_finished جديد بسبب إغلاق الإعلان فقط. تنقل الموقع المقصود يظل مسموحاً.
- renderer_gone يسجل إن كان محرك WebView قد تعطل أو قُتل؛ لا يمكن الاحتفاظ بحالة JavaScript داخل محرك مات بالفعل، ولا نعالج ذلك بإخفائه أو إعادة تحميل صامتة.
- onResume لا يعيد تحميل الصفحة ولا يخفي WebView ولا يشغّل المزامنة. المزامنة الأولية والدورية المُعدّة مسبقاً تبقى؛ إن وصل تغيير رابط أثناء إعلان كامل الشاشة يُحفظ للتشغيل التالي دون نقل الصفحة الحالية.
- تهيئة MobileAds.initialize تحدث في NativeApplication على خيط AdMobInit الخلفي باستخدام Application context فقط، مرة واحدة بعد نجاحها لكل عملية. لا تحتوي مهمة الخلفية على Activity أو WebView أو تحميل أو عرض إعلان، وتعود إشعارات النجاح والفشل إلى Main Thread.
- NativeApplication مسجلة في AndroidManifest وتبدأ التهيئة عند إقلاع التطبيق إن كانت الإعلانات مفعّلة وجمع الموافقة غير مفعّل؛ عند تفعيل الموافقة تنتظر سماح UMP بطلب الإعلانات ولا تتجاوزه. الموافقة وتحميل الإعلانات وعرضها وAdView تبقى على Main Thread كما هي، ولا يتغير منطق الموقع أو توقيت عرض الإعلانات.
- للتحقق على جهاز Android: ابنِ وثبّت APK جديداً، وانتظر دقيقتين على الأقل بعد بداية التهيئة. يجب أن يظهر sdk_initialize_begin thread=AdMobInit مرة واحدة في العملية الناجحة، ثم sdk_initialize_callback وsdk_initialize_complete. عدم العرض وحده لا يعزل التهيئة عن التحميل المسبق؛ استخدم نسخة التشخيص المعطلة فيها جميع أنواع الإعلانات كما ذُكر أعلاه.
- لا يوجد WebView Ads API ولا Activity إعلانات مخصصة؛ يستخدم Google SDK واجهته الأصلية.
- AdUi يمسك RuntimeException في نقطة التنفيذ الفعلية، بما فيها Runnable المؤجل على Main Thread، ويسجل اسم العملية والاستثناء كاملاً في NativeBuilderAds. تُحرّر أعلام التحميل/العرض والتهيئة عند فشل الاستدعاء، ولا توجد إعادة محاولة تلقائية متكررة أو إعادة تحميل للموقع.
- حاوية البانر بعرض match_parent وارتفاع ثابت 50dp، وAdView بحجم 320×50dp في منتصفها. الحاوية شقيقة مستقلة لـ SwipeRefreshLayout وليست داخل منطقة تمرير WebView؛ تبقى طبقة عائمة كما كانت، ولا تُضاف هوامش أو تغييرات لمساحة الموقع.
- إخفاء البانر وحاويته يستخدم INVISIBLE بدلاً من GONE للحفاظ على القياسات. طلبات البانر المتكررة لا تعيد إضافة AdView أو تطبيق LayoutParams نفسها؛ لا يُعاد تغيير موضع الحاوية إلا إذا طلب الموقع موضعاً مختلفاً. فشل تجهيز البانر ينظف العرض الجزئي بدلاً من ترك طبقة عالقة.
- التحديث التلقائي للبانر إعداد في حساب AdMob، وليس مفتاحاً محلياً في التطبيق: Apps → التطبيق → Ad units → وحدة البانر → Advanced settings → Automatic refresh → Disabled → Save. ويمكن اختيار معدل مخصص بين 30 و150 ثانية بدلاً من تعطيله. مرجع Google: https://support.google.com/admob/answer/3245199
- الكود يرسل طلب تحميل أولياً واحداً لكل AdView ولا ينشئ مؤقت إعادة تحميل؛ هذا لا يمنع التحديث الداخلي للـ SDK إذا ظل مفعّلاً في AdMob. لا نوقف AdView.pause أثناء عرضه للتحايل على التحديث، وتبقى pause/resume مرتبطة بالإخفاء ودورة حياة التطبيق.
- ظهور المشكلة بعد دقيقة لا يثبت وحده أن التحديث التلقائي هو السبب؛ قارن على Android بعد تعطيله من AdMob وانتظر عدة دقائق، مع مراجعة السجل. تثبيت الحاوية لا يعزل WebView عن كل ضغط ذاكرة أو تعطل GPU محتمل.
- try/catch يعالج استثناءات Java في مسار الإعلانات فقط؛ لا يمنع موت عملية Chromium/GPU أو نفاد الذاكرة، ولا يُعد دليلاً أن مشكلة جهاز معيّن قد حُلّت. تأكيد ذلك يتطلب اختبار APK جديد ومراجعة السجل على Android.
- شاشة البداية «سينمائي داكن»: تدرّج خفيف أسفل الشاشة + توهّج إشعاعي خلف الشعار (splash_wash.xml و splash_glow.xml)، ومربّع شعار بحدود رقيقة (icon_mark.xml)، ودخول متتابع للشعار ثم النصوص عبر PathInterpolator(0.22,1,0.36,1) بمدة 720ms وخطوة 140ms ورفع 16dp، ونبض نقاط 1150ms لكل نقطة بقمة عند 40% وتأخير 160ms. هذه الحركات أصلية داخل شاشة البداية فقط ولا تمس WebView ولا منطق الإعلانات.
- زاوية التدرّج في الاستوديو (0 = لأعلى) تُحوَّل إلى زاوية Android (0 = لليسار) بصيغة (450 − الزاوية) % 360، حتى يتطابق اتجاه التدرّج في المعاينة مع التطبيق المولّد.

## العمل بدون إنترنت من أول تشغيل
في وضع التنزيل الموسّع تُسحب الصفحات والموارد العامة المرتبطة أثناء بناء GitHub إلى `app/src/main/assets/site` مباشرة على القرص، بلا سقف 12MB أو 25 صفحة من الاستوديو.
التنزيل محدود فعلياً بوقت البناء ومساحة القرص وحجم APK الممكن، وليس لانهائياً. ملفات ZIP تتضمن أداة التنزيل؛ شغّلها قبل البناء المحلي.
يُنتج تقرير `snapshot-report.json` بالأحجام والملفات التي فشلت؛ يتوقف البناء عند نقص ملف بدلاً من الادعاء باكتمال النسخة.
لا تُنسخ قواعد بيانات الخادم أو تسجيل الدخول أو كل البيانات المنشأة ديناميكياً؛ هذه الوظائف قد تحتاج الإنترنت حتى مع حفظ الملفات.

## البناء مباشرة من GitHub
ارفع المشروع من الاستوديو إلى مستودع GitHub وسيبني الإجراء `.github/workflows/build-apk.yml` النسخ جاهزة،
ثم حمّل الـ APK من تبويب Actions.

## أين أعدّل ما أريد؟
كل الإعدادات في ملف واحد: `app/src/main/java/com/mystudio/app/AppConfig.java`
(الرابط، مدة شاشة البداية، الإعلانات، سحب للتحديث، كود JavaScript).
تصميم شاشة البداية في `app/src/main/res/layout/view_splash.xml`.

> ملاحظة: لتشغيل الإعلانات فعلياً يجب أن يكون حساب AdMob مفعّلاً وأن تُقبل المعرّفات — الوضع التجريبي يعمل دائماً للتأكد من عدم وجود مشاكل.
